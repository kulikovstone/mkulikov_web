# Развёртывание mkulikov.com

## Сервер и схема публикации

Используется VDS `136.234.5.71` (`luann`, Ubuntu 24.04), на котором также работает
«Сообщество кураторов». Схема повторяет статический фронт проекта `curator_web`:
сборка в GitHub Actions, передача архива по SSH, атомарное переключение версии.

| Что | Значение |
| --- | --- |
| Репозиторий | `kulikovstone/mkulikov_web` |
| Ветка публикации | `master` |
| Адрес | `https://mkulikov.com/` |
| SSH-пользователь | `mkulikov-web-deploy`, без sudo |
| Версии | `/var/www/mkulikov/releases/<commit>-<run-id>-<attempt>` |
| Текущая версия | `/var/www/mkulikov/current` |
| Nginx | `/etc/nginx/sites-available/mkulikov` |
| Команда деплоя | `/usr/local/bin/deploy-mkulikov-web` |
| Сертификат | `/etc/letsencrypt/live/mkulikov.com/` |

Сервер и HTTPS настроены 13 октября 2026 года; исходная версия сохранена как
`bootstrap-20261013T062756Z`. Сертификат Let's Encrypt действует до 11 января
2027 года, автоматическое продление включено. Публичный DNS может некоторое
время возвращать прежний адрес из кеша.

## Однократная настройка GitHub

В репозитории откройте **Settings → Secrets and variables → Actions →
New repository secret** и добавьте:

- Имя: `DEPLOY_SSH_KEY`.
- Значение: полный приватный ключ из
  `/home/mkulikov/.ssh/mkulikov_web_github_actions`, включая начальную и конечную строки.

Это отдельный ключ только для личного сайта. Не используйте ключи кураторов,
не добавляйте приватный ключ в Git и не отправляйте его в чат.
Публичная часть уже установлена на VDS. Приватная часть на сервер не передаётся.

Отправьте подготовленные изменения в `master`, затем проверьте зелёный запуск
**Actions → Deploy website**. Сам по себе локальный коммит workflow не запускает.
Описание механизма секретов: [GitHub Docs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

## Как работает деплой

1. Actions получает код, устанавливает Node.js 22 и выполняет `npm ci`.
2. Проверяет Bash-скрипты и запускает тесты проверки архивов, ограничений SSH,
   переключения версий и отката.
3. `npm run build` создаёт `dist/`.
4. `deploy/publish.sh` передаёт архив пользователю `mkulikov-web-deploy`.
5. Сервер проверяет архив и распаковывает его в новый каталог версии.
6. Атомарно переключает ссылку `current`.
7. Проверяет через локальный Nginx, что HTTPS с действительным сертификатом
   отдаёт точный `index.html` новой версии. При ошибке возвращает прежнюю ссылку;
   workflow завершается с ошибкой.

Публикации сериализованы в Actions и файловой блокировкой на VDS. Для повторения
неудачного запуска используйте **Re-run jobs**: номер попытки создаст новый каталог.
Обновления сайта не требуют перезапуска Nginx. Старые версии сохраняются;
автоматическая очистка пока не настроена.

SSH-ключ разрешает только команду `deploy <commit>-<run-id>-<attempt>`.
Интерактивный вход и forwarding запрещены. Команда деплоя и `authorized_keys`
принадлежат root. Архив не может содержать ссылки, скрытые файлы или пути за
пределами каталога версии. Лимиты: 20 MiB архива, 100 MiB файлов, 2000 записей.
Ожидаемый публичный ключ VDS закреплён в `deploy/known_hosts` и сверён через
административный SSH-доступ. Не отключайте `StrictHostKeyChecking`.

## Первоначальная установка на существующий VDS

Для текущего сервера настройка HTTP и SSH уже выполнена. Скрипт установки
отказывается перезаписывать существующие каталоги и пользователя.

Для повторения на подготовленном Ubuntu-сервере нужны Nginx, Certbot, Python 3,
curl и OpenSSH. Передайте каталог `deploy/`, готовый `dist/` и **публичный** ключ.
Под root выполните:

```bash
bash deploy/setup-server.sh /path/to/deploy-key.pub /path/to/dist
```

Скрипт создаёт пользователя и каталоги, устанавливает ограниченную команду
деплоя и отдельный HTTP virtual host. Конфигурация кураторов не редактируется.

A-запись `mkulikov.com` должна указывать на `136.234.5.71`. Лишней AAAA-записи
быть не должно: IPv6-публикация в этой настройке не подготовлена. Затем под root:

```bash
enable-mkulikov-https
```

Команда проверяет DNS, использует существующий ACME-аккаунт сервера для выпуска
отдельного сертификата, включает HTTPS и HTTP → HTTPS, проверяет конфигурацию
перед reload и включает `certbot.timer`. HTTP challenge остаётся доступным для
продления; deploy-hook Certbot перезагружает Nginx после обновления сертификата.
В существующие конфигурации и сертификаты кураторов изменения не вносятся.

Исходники `setup-server.sh`, `enable-https.sh`, `nginx-*.conf` и
`server/deploy-site.py` сами через Actions на VDS не устанавливаются.
Изменение серверной инфраструктуры выполняется отдельно под root.

## Диагностика и откат

На сервере под root:

```bash
nginx -t
readlink /var/www/mkulikov/current
ls -lt /var/www/mkulikov/releases
curl --fail --resolve mkulikov.com:443:127.0.0.1 https://mkulikov.com/
systemctl status certbot.timer --no-pager
```

Чтобы вернуть сохранённую версию, замените `ИМЯ_ВЕРСИИ` на существующий каталог:

```bash
flock /var/www/mkulikov/.deploy.lock bash -c '
  set -e
  cd /var/www/mkulikov
  test -s "releases/ИМЯ_ВЕРСИИ/index.html"
  ln -s "releases/ИМЯ_ВЕРСИИ" .current-manual
  mv -Tf .current-manual current
'
```

После отката проверьте HTTPS. Прежние папки версий можно очищать вручную,
сохраняя текущую и хотя бы одну предыдущую рабочую версию.
